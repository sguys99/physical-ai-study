### 1.2 성공 판정 기준

**① assert 5종이 8개 레벨 구성에서 전부 통과합니다. 왕복오차가 정확히 0이어야 합니다.**

```
=== [1] 자체 검증 — 왕복 · 인덱스 범위 · 유일성 · STE · 채널별 레벨 ===
  [OK] L=[8, 6, 5]  d=3  |C|=240  왕복오차=0.00e+00  STE오차=1.19e-07  채널별 레벨=[8, 6, 5]
  [OK] L=[8, 5, 5, 5]  d=4  |C|=1,000  왕복오차=0.00e+00  STE오차=5.96e-08  채널별 레벨=[8, 5, 5, 5]
  [OK] L=[7, 5, 5, 5, 5]  d=5  |C|=4,375  왕복오차=0.00e+00  STE오차=1.19e-07  채널별 레벨=[7, 5, 5, 5, 5]
  [OK] L=[8, 8, 8, 6, 5]  d=5  |C|=15,360  왕복오차=0.00e+00  STE오차=1.19e-07  채널별 레벨=[8, 8, 8, 6, 5]
  [OK] L=[8, 8, 8, 5, 5, 5]  d=6  |C|=64,000  왕복오차=0.00e+00  STE오차=5.96e-08  채널별 레벨=[8, 8, 8, 5, 5, 5]
  [OK] L=[3, 3, 3]  d=3  |C|=27  왕복오차=0.00e+00  STE오차=5.96e-08  채널별 레벨=[3, 3, 3]
  [OK] L=[4, 4]  d=2  |C|=16  왕복오차=0.00e+00  STE오차=5.96e-08  채널별 레벨=[4, 4]
  [OK] L=[8, 8]  d=2  |C|=64  왕복오차=0.00e+00  STE오차=5.96e-08  채널별 레벨=[8, 8]
  → 5종 assert 전부 통과. 짝수 L([4,4] · [8,8])에서도 격자가 정확히 L개입니다.
```

| 판정 항목 | 기대 | 왜 이 값이어야 하는가 |
|---|---|---|
| **왕복오차** | 정확히 `0.00e+00` | `indices_to_codes(codes_to_indices(ẑ)) == ẑ`. **여기가 0이 아니면 토큰이 액션을 잃습니다.** 부동소수점 오차가 아니라 정확히 0이어야 하는 이유는 자릿수 연산이 정수 격자 위에서만 돌기 때문입니다 |
| **STE오차** | `1e-7` 근방 | 자동미분이 흘린 그래디언트와 해석해 $f'(z)/\lfloor L/2 \rfloor$ 의 차이. float32 정밀도 한계라 0이 아닌 것이 정상입니다 |
| **`[4,4]`·`[8,8]` 통과** | `[OK]` | **짝수 $L$**. lesson §5.1이 "짝수 L에는 비대칭 $f$가 필요하다"고 한 부분의 검증입니다 |

**② Table 1 검산 — 곱이 240 / 1,000 / 4,375 / 15,360 / 64,000입니다.**

```
target |C| |    L (Table 1)     | d | prod L_i | prod/target | bits
-----------+--------------------+---+----------+-------------+------
   2^8     | [8, 6, 5]          | 3 |      240 |       0.938 |  7.91
   2^10    | [8, 5, 5, 5]       | 4 |    1,000 |       0.977 |  9.97
   2^12    | [7, 5, 5, 5, 5]    | 5 |    4,375 |       1.068 | 12.10
   2^14    | [8, 8, 8, 6, 5]    | 5 |   15,360 |       0.938 | 13.91
   2^16    | [8, 8, 8, 5, 5, 5] | 6 |   64,000 |       0.977 | 15.97
```

> **`prod/target`이 1.000이 아닌 것이 정상입니다.** lesson §5.3과 퀴즈 7번이 말한 그대로 — 코드북 크기가 2의 거듭제곱이어야 할 이유가 없습니다. 논문 표현도 "approximately match"입니다.
> 그리고 **$d$가 3 → 6으로 늘어날 뿐 $L_i$는 5~8에 머무는 것**을 보세요. 목표 크기를 키우는 방법이 "레벨을 키우기"가 아니라 **"채널을 늘리기"** 입니다. lesson 「흔한 오해」 4번가 지적한 부분입니다.

**③ ★ `nn.Parameter : 0개` — 이 한 줄이 이 스크립트의 결론입니다.**

### 1.4 확인 질문 (worksheet ②에 기록)

1. **`nn.Parameter`가 0개인 것이 왜 중요한가?**
   "파라미터가 적어서 좋다"는 절반짜리 답입니다. lesson §4.1의 닭-달걀 논리와 §7.2의 인터페이스 버전 관리를 각각 연결해 두 문장으로 쓰세요.
   <details><summary>방향 힌트</summary>

   ① **collapse의 원천 차단** — 코드워드가 파라미터가 아니면 "그래디언트를 못 받아 죽는" 일 자체가 성립하지 않습니다(lesson §5.2). ② **공유 상태의 소멸** — 코드북은 상위와 하위가 공유해야 할 텐서였습니다(lesson §4.2). 그게 없으면 상하위 계약이 정수 하나로 닫힙니다.
   </details>

2. **짝수 $L$에서 비대칭 오프셋이 필요한 이유는?**
   `bound()`가 홀수 $L$에서는 `offset = 0`인데 짝수에서는 `0.5`를 씁니다. **격자점의 위치를 직접 그려보면** 이유가 바로 보입니다. $L=5$와 $L=4$일 때 $\mathrm{round}$가 만드는 정수 집합을 각각 적어보세요.
   <details><summary>방향 힌트</summary>

   $L=5$면 $\lfloor 5/2 \rfloor = 2$이고 $\tanh$ 출력을 $[-2, 2]$로 늘려 반올림하면 $\{-2,-1,0,1,2\}$ — 정확히 5개이고 **0을 중심으로 대칭**입니다. $L=4$면 $[-2, 2]$에서 반올림하면 $\{-2,-1,0,1,2\}$로 **5개가 나와버립니다.** 반 칸을 밀어 격자 중심을 어긋나게 해야 정확히 4개가 됩니다. 위 ①에서 `[4,4]`·`[8,8]`을 굳이 검증 목록에 넣은 이유입니다.
   </details>

3. **`bits` 열이 정수가 아닌 것**(7.91 / 9.97 / 12.10 …)은 무엇을 뜻하는가? 실제로 저장할 때는 몇 비트를 쓰게 되는가? (→ Step 4의 압축률과 이어집니다)

### 1.5 심화 — $L_i \ge 5$ 휴리스틱을 위반해 보기

lesson §5.3의 휴리스틱은 "모든 $i$에 대해 $L_i \ge 5$"입니다. 논문은 근거를 자세히 쓰지 않고 "실험 전반에서 잘 동작했다"고만 합니다. **직접 위반해서 무엇이 나빠지는지 보세요.**

> 📌 **FSQ 자체는 멀쩡히 동작합니다.** 휴리스틱을 어겼다고 코드가 깨지지는 않습니다. 나빠지는 것은 **채널 효율**입니다.

**여기서 읽을 것 — 같은 $d=3$인데 코드 수가 다릅니다.**

| $\mathcal{L}$ | $d$ | $\|\mathcal{C}\| = \prod L_i$ | bits/token |
|---|---|---|---|
| `[4, 4, 4]` (휴리스틱 위반) | **3** | **64** | 6.00 |

**복원 성능까지 보고 싶으면** (약 50초, Step 3의 표와 나란히 놓고 보세요):

> ① **같은 $d=3$인데 `[8,6,5]`가 `[4,4,4]`보다 복원이 훨씬 낫습니다**(0.00781 vs 0.01010). 채널 예산을 낭비한 대가입니다.

### 2.2 무정보 베이스라인 — 왜 필요한가

`val MSE = 0.00583`이라는 숫자만 보면 좋은지 나쁜지 알 수 없습니다. **비교 대상이 필요합니다.**

베이스라인은 **"학습셋 평균 청크를 늘 그대로 뱉는 모델"** 의 검증 MSE입니다. 토큰을 하나도 안 쓰고, 입력도 안 보고, 그냥 평균만 답하는 모델입니다. 그 값이 **0.02173**입니다.

$$
\text{vs 기준선} = \frac{\text{val MSE}}{0.02173}
$$

이 비율이 **토큰 하나가 실제로 번 정보량**입니다. 27%면 "평균만 답할 때 대비 오차를 73% 줄였다", 97%면 "토큰이 사실상 아무 일도 안 했다"입니다.

> 제어 배경이면 익숙한 구도입니다. 식별 모델의 성능을 절대 잔차로 보고하지 않고 **분산 설명률(FIT %)이나 무모델 예측 대비**로 보고하는 것과 같은 이유입니다. 스케일이 데이터에 따라 달라지므로 절대값은 비교가 안 됩니다.

### 2.3 관절 시너지 — `--synergies 6`이 무슨 뜻인가

궤적을 29개 관절에서 **직접** 만들지 않고, 6차원 계수 공간에서 만든 뒤 고정 기저 $B \in \mathbb{R}^{6 \times 29}$로 관절 공간에 올립니다(practice README §3.2 eq.(7)).

```
x(t) = clip(x_stand + c(t)·B, −1, 1),   c(t) ∈ R^6
```

실제 휴머노이드 모션은 관절이 강하게 상관돼 **저차원 다양체 위에 놓입니다.** 걸을 때 무릎·발목·고관절이 따로 놀지 않습니다. 시너지 6은 그 구조를 흉내낸 것입니다.

**이게 왜 중요한가**: 압축은 데이터에 구조가 있을 때만 가능합니다. 토큰 하나(약 10 bits)로 16프레임 × 29관절을 담을 수 있는 이유는 그 14,848 bits 안에 **실제로는 6차원 정보밖에 없기 때문**입니다.

### 3.3 ★ 결과 해석 ① — VQ는 코드북을 키워도 쓰는 코드가 안 늘어난다

표에서 **`쓰인 코드` 열만** 따로 보세요. 사용률(%)이 아니라 **절대 개수**입니다.

```
             |C|      쓰인 코드
  VQ         256   →      214
  VQ       1,024   →      216      ← 코드북을 4배 키웠는데 +2개
  VQ       4,096   →      185      ← 16배 키웠는데 오히려 -29개

  FSQ        240   →      240
  FSQ      1,000   →      968      ← 4배 키우니 4배 늘어남
  FSQ      4,375   →    3,145      ← 18배 키우니 13배 늘어남
```

> 🔴 **이것이 codebook collapse의 가장 정확한 서술입니다.**
> "VQ는 사용률이 떨어진다"는 표현은 오해를 부릅니다 — 마치 코드북을 키우면 각 코드가 조금씩 덜 쓰이는 것처럼 들립니다.
> 실제로 일어나는 일은 **VQ가 쓸 수 있는 코드 수에 천장이 있고(여기서는 약 200개), 코드북을 키우면 분모만 커지는 것**입니다.
> 사용률 4.5%는 "코드를 4.5%만 쓴다"가 아니라 **"3,911개를 아예 안 쓴다"** 입니다.

**왜 200개에서 멈추는가?** lesson §4.1의 닭-달걀입니다. 학습 초기에 어쩌다 뽑힌 코드워드만 그래디언트를 받아 데이터 쪽으로 이동하고, 그러면 더 잘 뽑히고, 나머지는 초기 랜덤 위치에 그대로 남아 영원히 뽑히지 않습니다. **초기에 살아남은 코드 수가 사실상 최종 코드 수**입니다. 코드북을 키워도 살아남는 수는 안 늘어납니다.

> **제어 대응**: persistent excitation 조건이 깨진 식별 실험입니다. 여자(excitation)가 부족해 방문되지 않는 모드는, 파라미터를 아무리 많이 잡아도 끝내 식별되지 않습니다. **모델 차수를 올린다고 관측되지 않는 모드가 관측되지는 않습니다.**

**worksheet ④에 기록**: 본인 실행의 `쓰인 코드` 3개 값(VQ)과 3개 값(FSQ).

### 3.6 ★★ 함정 교정 — FSQ 사용률 100 → 96.8 → 71.9는 실패가 아니다

**이 절을 안 읽고 넘어가면 이 모듈에서 잘못된 결론을 갖고 나갑니다.**

표를 보면 FSQ 사용률도 코드북을 키울수록 내려갑니다.

```
  FSQ  |C|=  240  →  100.0%
  FSQ  |C|=1,000  →   96.8%
  FSQ  |C|=4,375  →   71.9%     ← 28.1%가 안 쓰였다
```

**논문은 "약 100%"라고 했는데 왜 71.9%인가?** 세 가지를 구분해야 합니다.

| 질문 | 답 |
|---|---|
| **구현이 틀렸나?** | 아닙니다. `01`의 assert 5종이 통과했고, 왕복오차가 0입니다 |
| **FSQ가 collapse한 건가?** | 아닙니다. collapse는 **코드워드가 학습되지 않아 죽는 것**이고, FSQ에는 학습되는 코드워드가 없습니다. 여기서 안 쓰인 격자점은 **죽은 게 아니라 갈 필요가 없었던 것**입니다 |
| **그럼 무엇인가?** | **데이터가 4,375가지 다양성을 안 가진 것입니다.** §2.3에서 봤듯 이 궤적은 6차원 시너지 다양체 위에 있습니다. 그 다양체를 덮는 데 3,145개면 충분했고, 나머지 1,230개 격자점은 **데이터가 존재하지 않는 영역**입니다 |

> **논문의 100%는 ImageNet 규모 데이터 기준입니다.** 이미지 한 장이 토큰 수백 개를 만들고, 데이터의 내재 차원이 이 장난감 궤적과 비교가 안 됩니다.
> 여기서 확인할 수 있는 것은 **"FSQ가 100%를 낸다"가 아니라 "FSQ의 사용률은 데이터가 결정하고, VQ의 사용률은 최적화가 결정한다"** 입니다.
>
> 판정하려면 **같은 데이터·같은 인코더에서 두 방법을 비교**해야 합니다. 그게 이 스윕의 설계이고, 그 비교의 답은 **71.9% vs 4.5%** 입니다. **16배 차이**입니다.

**추가 확인 — 사용률 상한**

스크립트가 각 구성마다 `사용률 상한=100.0%`를 찍습니다. 검증셋이 코드북보다 충분히 커야 사용률이 의미를 갖기 때문입니다.

$$
\text{usage} \le \min\left(1,\ \frac{N_{\text{val tokens}}}{|\mathcal{C}|}\right)
$$

기본 설정은 검증 토큰 28,800개(코드북 4,096의 7배)라 상한이 100%입니다. **상한이 100%가 아니면 사용률 숫자를 비교하면 안 됩니다** — `--n-val-traj`를 키우세요.

> 📌 **이건 액션 토크나이저 고유의 함정입니다.** 이미지 토크나이저는 이미지 한 장이 토큰 수백 개를 만들어 이 문제가 없습니다. 청크 하나가 토큰 하나인 액션 토크나이저는 **평가 설계에서 이것부터 걸립니다.** 회사 토크나이저를 평가할 때 물어야 할 질문 하나가 여기서 나옵니다.

### 3.7 심화 — VQ에 트릭을 켜면 해결되는가

lesson §4.1의 표에는 collapse 대응 트릭이 6가지 쌓여 있습니다. **"트릭을 넣으면 되는 거 아닌가"** 가 이 지점에서 나오는 가장 자연스러운 반문입니다. 직접 켜보세요.

```bash
MUJOCO_GL=egl python 02_fsq_vs_vq_g1.py --vq-init data --no-render     # 코드북을 데이터로 초기화
MUJOCO_GL=egl python 02_fsq_vs_vq_g1.py --vq-ema --no-render            # EMA 업데이트
MUJOCO_GL=egl python 02_fsq_vs_vq_g1.py --vq-init data --vq-ema --no-render
```

각 30~60초입니다. **집필 환경 실측**($|C|$=1024, 40 epoch, 같은 시드):

| 명령 | VQ 사용률 | val MSE |
|---|---|---|
| (기본) 바닐라 | **21.1%** | 0.00586 |
| `--vq-init data` | 19.5% | — |
| `--vq-ema` | 18.8% | 0.00591 |
| `--vq-init data --vq-ema` | **18.3%** | 0.00592 |

> 🔴 **이 설정에서는 트릭이 도움이 되지 않았습니다.** 셋 다 바닐라보다 사용률이 **낮게** 나왔습니다.
>
> **여기서 배울 것은 "트릭이 쓸모없다"가 아닙니다.** 논문 규모의 실험에서는 효과를 냅니다 — 그래서 lesson §4.1의 표에 6가지가 쌓인 것입니다.
> 배울 것은 **"논문의 트릭이 내 설정에 자동으로 이식되지 않는다"** 입니다. 각 트릭은 자기가 나온 설정(데이터 규모·모델 크기·학습 길이)의 가정을 달고 옵니다.
>
> 그리고 이것이 FSQ의 진짜 주장을 선명하게 만듭니다: **"트릭을 잘 고르면 된다"가 아니라 "그 표 자체가 필요 없다"** 입니다. 튜닝할 것이 없으면 튜닝이 실패할 일도 없습니다.

### 4.4 결과 해석 — 계단(zero-order hold)과 DAC 분해능

**`03_overlay.png`가 이 스크립트의 핵심 그림입니다.** 관절 4개에 대해 원본(실선)과 복원(계단)을 겹쳐 그립니다.

**복원 궤적이 계단 모양입니다.** 청크 하나 = 토큰 하나 = 계단 하나(16프레임 = 0.32초)이고, 청크 안에서는 디코더가 만든 궤적이 나옵니다.

> **lesson §3의 DAC 분해능 비유가 그림으로 나온 것입니다.**
> 12비트 DAC로 액추에이터를 구동하면 명령이 $2^{12}$개 격자 위에만 존재합니다. 여기서는 10비트($\log_2 1000 = 9.97$) DAC이고, **격자가 스칼라 값이 아니라 0.32초짜리 궤적 조각**이라는 것만 다릅니다.
> 그래서 던져야 할 질문도 DAC와 같습니다: **격자 간격이 제어에 필요한 분해능을 주는가? 두 격자 사이에서 리미트 사이클이 생기지 않는가? 데드밴드는 어디인가?**

**`03_joint_error.png` (b)** 에서 오차가 **가동범위에 비례**하는 것을 보세요. 정규화 공간에서 일하기 때문입니다(practice README §3.1 eq.(6)).

> **여기서 실무 설계 결정 하나가 나옵니다**: 손실에 **관절별 가중치**를 넣을 것인가? 발목(30°)과 어깨(330°)를 정규화 공간에서 똑같이 대우하는 것이 맞는가?
> 답은 "무엇을 위한 토크나이저인가"에 달려 있습니다. 균형 유지가 목적이면 발목 정밀도가 훨씬 중요하고, 조작이 목적이면 팔이 중요합니다. **팀 질문 후보입니다.**
