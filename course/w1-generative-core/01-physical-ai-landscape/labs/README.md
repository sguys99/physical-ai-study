## Step 2 — 주파수 예산을 손으로 흔들어 보기 (30분)

lesson §4.1의 부등식

$$H_{\text{chunk}} \;\ge\; f_2\bigl(T_{\text{replan}} + \tau_{\text{infer}} + \tau_{\text{comm}}\bigr), \qquad T_{\text{replan}} = 1/f_4$$

을 **몸에 붙이는 것**이 목적입니다.

> 🔴 **순서를 반드시 지키세요.** 각 시나리오마다
> **① 답을 먼저 손으로 계산해 [`worksheet.md`](worksheet.md)에 적고 → ② 그 다음에 스크립트를 돌려 검산합니다.**
> 먼저 돌려보면 숫자를 읽기만 하고 배움이 남지 않습니다. 이 부등식은 W2-M1(ACT)·W4-M4에서 다시 나옵니다.

기준선(인자 없이 돌렸을 때의 기본값): $f_2 = 50$ Hz, $f_4 = 5$ Hz, $\tau_{\text{infer}} = 100$ ms, $\tau_{\text{comm}} = 20$ ms → $H_{\text{required}} = 16$, 최악 반응 지연 320 ms.

### 시나리오 ① WBC를 200 Hz로 올리면? (`--f2 200`)

**먼저 손으로**: $H_{\text{required}}$는? 그리고 최악 반응 지연 $H/f_2$는 기준선(320 ms)보다 커질까 작아질까 같을까?

```bash
python 01_stack_frequency_budget.py --f2 200
```

**관찰할 것**: `H_required` 값, 그리고 `[5] 트레이드오프` 표의 `최악 반응지연[ms]` 열이 기준선과 비교해 어떻게 변했는가.

<details>
<summary>정답 (실제 실행 결과)</summary>

$H \ge 200 \times (0.2 + 0.1 + 0.02) = 200 \times 0.32 = 64$ 스텝.

```
  설정: f2=200Hz, f4=5Hz, tau=120ms, T_replan=200ms, H_chunk=63
  필요 최소 청크 길이 H_required = 64 스텝  (lesson §4.1 eq.(1))
  청크 도착 시 이미 만료된 앞부분 = 24 스텝  <- tau가 부등식에 들어가는 이유
  명령 공백률 =   2.39 %  (공백 발생)
```

```
H_chunk |    구간    | 공백률[%] | 최악 반응지연[ms]
--------+------------+-----------+------------------
     32 | 부족       |      78.7 |               160
     64 | 최소(권장) |       0.0 |               320
    128 | 여유       |       0.0 |               640
    256 | 과다       |       0.0 |              1280
```

**핵심 관찰**: 청크 길이는 16 → 64로 **4배**가 됐는데 **최악 반응 지연은 320 ms 그대로**입니다.
$H/f_2 = (f_2 \cdot \tau_{\text{total}})/f_2 = \tau_{\text{total}}$ 이므로 $f_2$가 약분돼 사라집니다.
즉 **하위 제어기를 빠르게 하는 것은 반응성을 개선하지 않습니다.** 반응 지연을 결정하는 것은 오직 상위 루프의 총 지연
$T_{\text{replan}} + \tau_{\text{infer}} + \tau_{\text{comm}}$ 입니다. 제어로 옮기면, inner loop 대역폭을 올려도
outer loop의 setpoint 갱신 주기가 그대로면 전체 추종 성능의 상한은 바뀌지 않는 것과 같습니다.

</details>

### 시나리오 ② 온보드 추론이 느릴 때 (`--tau-infer 0.300`)

**먼저 손으로**: $\tau_{\text{infer}}$가 100 ms → 300 ms로 3배가 되면 $H_{\text{required}}$는 몇 배가 될까? (3배가 아닙니다 — 왜인지도 적으세요.)

```bash
python 01_stack_frequency_budget.py --tau-infer 0.300
```

**관찰할 것**: `H_required`, `청크 도착 시 이미 만료된 앞부분`(stale head), 그리고 `[5]` 표의 `부족` 행 공백률.

<details>
<summary>정답 (실제 실행 결과)</summary>

$H \ge 50 \times (0.2 + 0.3 + 0.02) = 50 \times 0.52 = 26$ 스텝.

```
  설정: f2=50Hz, f4=5Hz, tau=320ms, T_replan=200ms, H_chunk=25
  필요 최소 청크 길이 H_required = 26 스텝  (lesson §4.1 eq.(1))
  청크 도착 시 이미 만료된 앞부분 = 16 스텝  <- tau가 부등식에 들어가는 이유
  명령 공백률 =   9.52 %  (공백 발생)
  최악 반응 지연 = H_chunk/f2 = 25/50 = 500.0 ms
```

```
H_chunk |    구간    | 공백률[%] | 최악 반응지연[ms]
--------+------------+-----------+------------------
     13 | 부족       |     100.0 |               260
     26 | 최소(권장) |       0.0 |               520
```

**핵심 관찰 2가지**

1. $\tau_{\text{infer}}$가 3배가 됐는데 $H$는 16 → 26으로 **1.6배**만 늘었습니다. 괄호 안에 $T_{\text{replan}} = 200$ ms가
   상수로 깔려 있기 때문입니다. 추론을 아무리 빨리 만들어도 $H$는 $f_2 \cdot T_{\text{replan}} = 10$ 스텝 아래로 못 내려갑니다.
   **재계획 주기가 바닥을 만듭니다.**
2. `부족`(H=13) 행의 공백률이 **100%** 입니다. 청크가 커버하는 시간 $13/50 = 260$ ms가 도착 지연 $\tau = 320$ ms보다
   짧아서, 청크가 L2에 도착하는 순간 **이미 전부 만료**돼 있습니다. stale head 16 스텝 > H 13 스텝. 한 스텝도 못 씁니다.

</details>

### 시나리오 ③ 청크가 부족할 때의 공백률 (`--h-chunk 8`)

**먼저 손으로**: $H_{\text{required}} = 16$인데 8만 준다면 공백률은? (힌트: 청크는 $t_k + \tau$에 도착해 $t_k + H/f_2$까지만 유효합니다. $\tau = 120$ ms, $H/f_2 = 160$ ms, 재계획 주기 200 ms.)

```bash
python 01_stack_frequency_budget.py --h-chunk 8
```

**관찰할 것**: 공백률 수치와 ASCII 타임라인의 **주기 패턴**.

<details>
<summary>정답 (실제 실행 결과)</summary>

**손계산(연속 근사)**: 청크 하나가 덮는 구간은 $[120, 160)$ ms — 폭 40 ms. 재계획 주기는 200 ms.
따라서 duty = 40/200 = 20% → **공백률 약 80%**.

**스크립트(이산 스텝)**: 78.72%.

```
  설정: f2=50Hz, f4=5Hz, tau=120ms, T_replan=200ms, H_chunk=8
  필요 최소 청크 길이 H_required = 16 스텝  (lesson §4.1 eq.(1))
  청크 도착 시 이미 만료된 앞부분 = 6 스텝  <- tau가 부등식에 들어가는 이유
  명령 공백률 =  78.72 %  (공백 발생)
  최악 반응 지연 = H_chunk/f2 = 8/50 = 160.0 ms
  타임라인 첫 60스텝 ('#'=명령 있음, '.'=공백):
    |......##........##........##........##........##........##..|
```

**80% vs 78.72% — 어느 쪽이 맞는가?** 둘 다 맞고, 차이는 두 가지 이산화 효과입니다.

- 통계 구간에서 **워밍업(첫 청크 도착 전 6스텝)을 제외**합니다. 2.0초 = 100스텝 중 94스텝만 분모.
- 20 ms 격자에서 $[120, 160)$ ms 안에 들어가는 스텝은 120·140 **두 개**뿐입니다(160은 배타). 10스텝 주기당 2스텝 = 20%.
  마지막 재계획분이 시뮬 끝을 넘어가 잘리면서 분자가 조금 더 줄어 $1 - 20/94 = 78.72\%$.

손계산은 **정상상태 duty**, 스크립트는 **유한 구간 실측**입니다. 설계 판단에는 손계산으로 충분하고,
스크립트는 "경계에서 실제로 몇 스텝이 잘리는가"를 보여줍니다.

</details>

### 마무리 질문 (worksheet에 서술)

> **L4 추론을 300 ms로 만드는 대신 청크를 늘리는 선택의 대가는 무엇인가?**

답에 반드시 포함할 것:

- lesson §4.3 트레이드오프 — 최악 반응 지연 $= H_{\text{chunk}}/f_2$가 **선형으로 커진다**. 시나리오 ②에서 320 ms → 520 ms.
- 청크 실행 중에는 **새 관측을 반영하지 못한다**. 외란·환경 변화에 그만큼 늦게 대응한다.
- MPC 대응 — 예측 지평 $N$을 늘리는 것과 같은 구조. MPC에서 $N$을 늘리면 계산량과 **모델 오차 누적**이 늘고,
  여기서는 계산량 대신 **정책의 예측 오차 누적**이 늘어난다. 둘 다 "열린 루프로 미래를 얼마나 길게 믿을 것인가" 문제다.
- 그래서 실무 해법은 보통 둘 중 하나가 아니라 **재계획 주기를 짧게 유지하면서 청크를 겹쳐 쓰는 것**(temporal ensembling).
  → W2-M1(ACT)에서 다시 만납니다.

### 3.4 `02_stack_layers.png` — 어느 경계가 가장 넓은가

y축 라벨에 비율이 같이 찍혀 있습니다.

```
L5 · 인지·매핑        (L4 대비 ÷2.0)      0.5–5 Hz
L4 · 상위 지능        (L2 대비 ÷50)       1–10 Hz
L3 · 액션 인터페이스  (이벤트 구동)        [빗금 — 고정 주파수 없음]
L2 · 전신 제어 WBC    (L1 대비 ÷8.9)      50–500 Hz
L1 · 하드웨어·미들웨어 (기준)             1,000–2,000 Hz
```

읽어야 할 것 세 가지.

1. **가장 넓은 경계는 L2↔L4(×50)입니다.** L1↔L2는 ×8.9로 그 다음입니다.
   즉 이 스택에서 **진짜 큰 벽은 "실시간 제어 루프"와 "신경망 추론 루프" 사이**에 있습니다.
   L3(액션 인터페이스)가 하필 이 자리에 놓여 있는 것이 우연이 아닙니다 — **가장 넓은 틈에 다리를 놓는 것**이 L3의 일입니다.
2. **L4↔L5는 ×2.0에 불과합니다.** `01`의 대역폭 분리비 표는 이 경계를 `약함`으로 판정하고, 최악 조건에서는 밴드가 역전(×0.20)합니다.
   이 둘은 대역폭 분리가 아니라 **기능 분리**(인지 vs 행동 의도)입니다.
3. **L3만 빗금 막대**입니다. 고정 주파수가 없는 이벤트 구동 계층이라 x축 위에 점을 찍을 수 없습니다.

> 📌 **문서와 출력이 어긋나면 출력을 믿으세요.** 이 자료도 집필 중에 산문이 `01`의 분리비 표와
> 어긋난 적이 있습니다(“L1↔L2가 가장 넓다”고 잘못 적혀 있었고, 지금은 고쳐졌습니다).
> 수치는 스크립트가 매번 다시 계산하지만 산문은 한 번 쓰면 굳습니다. 앞으로 어느 자료를 읽든
> **표·그림과 설명이 다르면 계산된 쪽이 맞다**고 보고, worksheet의 "내가 발견한 불일치" 칸에 적어두세요.

### 3.5 `03_player_landscape.png` — L3 열이 비어 있다

**(a) 누가 어느 계층에 베팅했는가** 패널에서 11개 조직 × 7개 열(L1~L5 + SIM + DATA) 매트릭스를 보면
**`L3 액션 인터페이스` 열에 채워진 칸이 하나도 없습니다.** `03 --smoke`의 stdout도 같은 말을 합니다.

```
  L1 하드웨어             (4) : Unitree, Figure AI, Tesla, 1X
  L2 전신 제어            (3) : NVIDIA GEAR, Google DeepMind, Shanghai AI Lab / InternRobotics
  L3 액션 인터페이스      (0) : -
  L4 상위 지능            (5) : NVIDIA GEAR, Physical Intelligence, Google DeepMind, ...
```

**이것이 lesson §3.5의 "승부처는 L3"와 맞물리는 핵심 관찰입니다.**
공개 논문 수준에서 액션 인터페이스를 **독립 계층으로 내세운** 조직이 사실상 없습니다.

회사가 FSQ 기반 계층 모델을 별도 계층으로 세운 것은, 남들이 부품으로 취급하는 것을 **인터페이스로 승격**시킨 베팅입니다.

> 이 관찰의 한계도 같이 적어두세요: 비어 있는 이유가 "아무도 안 한다"가 아니라
> **"공개 자료에서 그렇게 분류되지 않는다"** 일 수 있습니다. `players.csv`의 `bet_layers` 열은 필자의 분류이지
> 각 조직의 자기 선언이 아닙니다. Step 5의 SONIC 데모를 볼 때 이 점을 염두에 두세요.

**(b) 발표 타임라인** 패널에서는 점의 채움 여부를 보세요. **채운 점 = 1차 출처로 확인된 날짜, 빈 점 = 연/월만 아는 추정**입니다.

### 심화 ① `players.csv`에 최근 발표를 한 줄 추가해 그림 갱신

`03_player_landscape.py`는 코드를 고칠 필요가 없습니다. **CSV 한 줄이 곧 그림 한 줄**입니다.

```bash
cd course/w1-generative-core/01-physical-ai-landscape/practice
head -2 players.csv                 # 컬럼 규약 확인
$EDITOR players.csv                 # 한 줄 추가
python 03_player_landscape.py
```

지켜야 할 규약 두 가지(`03_player_landscape.py` 상단 마크다운 셀에 정의돼 있습니다).

- `date`는 **아는 만큼만** — `2026` / `2026-04` / `2026-04-16`. 모르면 빈칸에 `date_confidence=unknown`.
  연도만 아는 항목은 타임라인에 **그 해 전체를 덮는 막대**로 그려집니다. 없는 정밀도를 지어내지 않기 위한 장치입니다.
- **1차 출처로 확인되지 않은 수치는 넣지 마세요.**

**성공 판정**: 재실행 후 `[1]` 표의 마지막 줄 총계(`총 11개 조직 ...`)가 **12개로** 늘고,
`(b)` 패널에 새 행이 생기며, 확실성에 맞는 **채운 점 / 빈 점**으로 그려집니다.

**여기서 배우는 것**: 이 분야의 지형도는 몇 주 단위로 낡습니다. **낡지 않게 만드는 법은 코드가 아니라 데이터 파일로 분리하는 것**이라는
설계 습관 — W4-M5 캡스톤 문서에도 같은 원칙을 적용하게 됩니다.

### 심화 ② 우리 회사 실제 수치로 §4.1 부등식을 다시 풀기

지금까지 쓴 $\tau_{\text{infer}} = 100$ ms, $f_2 = 50$ Hz는 **논문 일반 범위이지 우리 수치가 아닙니다.**
팀에서 실측치를 받아 다시 푸는 것이 이 과제입니다. → 팀 질문 **M1-6**("L4 추론은 G1 온보드인가 외부 워크스테이션인가")과 직결됩니다.

받아야 할 값 4개.

| 기호 | 무엇 | 왜 필요한가 |
|---|---|---|
| $f_2$ | WBC 정책의 실제 제어 주파수 [Hz] | 청크 스텝 수의 스케일을 결정 |
| $f_4$ | 상위 모델 재계획 주파수 [Hz] | $T_{\text{replan}}$ = 부등식의 바닥 |
| $\tau_{\text{infer}}$ | L4 1회 추론 지연 [s] | **온보드 vs 외부에 따라 자릿수가 달라짐** |
| $\tau_{\text{comm}}$ | 통신 왕복 지연 [s] | 외부 추론이면 여기가 지배적일 수 있음 |

```bash
python 01_stack_frequency_budget.py --f2 <실측> --f4 <실측> --tau-infer <실측> --tau-comm <실측>
```

**성공 판정**: 실측 기반 $H_{\text{required}}$와 최악 반응 지연을 worksheet에 적고,
그 값이 **현재 회사 파이프라인의 실제 청크 길이와 맞는지** 팀에 되묻는 질문을 하나 더 만든다.
(맞지 않으면 둘 중 하나입니다 — 내 모델이 단순하거나, 파이프라인에 명령 공백이 있거나. 어느 쪽인지 묻는 것이 좋은 질문입니다.)

**여기서 배우는 것**: 수식은 숫자를 넣기 전까지 아무 말도 하지 않습니다.
$\tau_{\text{infer}}$ 하나가 온보드/외부 여부에 따라 자릿수로 달라지고, 그게 곧 **아키텍처 결정**이 됩니다.
W4-M4에서 이 값들을 다시 씁니다.
